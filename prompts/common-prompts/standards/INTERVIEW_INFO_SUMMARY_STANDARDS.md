# INTERVIEW_INFO_SUMMARY_STANDARDS（面试信息汇总 HTML 规范）

| 项目 | 内容 |
|---|---|
| 更新时间 | 2026-11-11 |
| 目的 | INTERVIEW_INFO_SUMMARY_STANDARDS 回答的是 HOW TO BUILD INTERVIEW PAGES：Human 当面试官时，AI 给 Human 准备的面试 HTML 页面必须怎么分层、怎么出题、怎么画图。 |
| 适用范围 | Human 要求 AI 准备面试资料（面试题、答案标准、补课页、面试当天看的页面）并做成 HTML 时适用。Human 自己去面试别人公司（Human 是候选人）时不适用。 |
| 和其他规则的关系 | 在 `prompts/common-prompts/rules/INFO_SUMMARY_HTML_RULES.md` 和 `prompts/common-prompts/rules/HTML_PAGE_RULES.md` 的基础上写面试页的不同之处；两者冲突时，面试页以本文件为准。共用 CSS/JS、颜色、字号、1500 字上限、图号、手机菜单仍按那两个文件。 |
| 对应的 Review | `prompts/common-prompts/review/INTERVIEW_INFO_SUMMARY_REVIEW.md`；本文件规定"必须怎么做"，Review 只检查"有没有做到"。 |
| 文档语言 | 本文件中文为主；technical terms、产品名、English 面试题保留 English。 |

## Mandatory Requirements

### 页面分层和数量

| 规则 | 一句话说白了 |
|---|---|
| 放在哪 | 面试页和工作用的信息汇总分开放：放在 project-root `interview-info-summary/`（项目 `PROJECT_LOCAL_OVERRIDES.md` 指定了别的位置时按它），样式和脚本引用 `info-summary/assets/` 的共用 `summary.css`、`summary.js`。 |
| 三层 | 第 1 层是面试总索引 `面试-信息汇总-Summary-索引.html`；第 2 层是面试综合页，一个岗位一页，这个岗位的所有候选人共用；第 3 层是专题页，补课用。没有单独的岗位页和候选人页：岗位要求画在综合页里，当前候选人的内容放在综合页最后一节。 |
| 面试当天只看综合页 | 综合页必须单独够用：面试官只看这一页，就能控制时间、出题、判断答案、查听不懂的名词、面完填 Feedback 表；不能要求面试官当天再去翻专题页。 |
| 专题越少越好 | 先问 Human 面试时长和技术题时长，再定专题数量：只留两类，一是和这份工作（合同或项目）直接相关的 must-have，二是面试官自己最擅长、能拿来判断候选人整体水平的领域。其他 must-have 并进这些专题，或者做成某道题的追问；加分项不单独成专题。开始写之前，先把“留哪些、去掉哪些、并到哪里”列给 Human 确认。 |
| 题目只放综合页 | 所有面试题只出现在综合页；专题页只放补课图，原来放题和名词的位置都改成一个链接，指到综合页。 |
| 文件名 | `YYYY-MM-DD-<岗位>-<主题>-信息汇总-Summary.html`，例如 `2026-11-04-genesis-SRE-面试综合页-信息汇总-Summary.html`。 |

### 页面结构

| 规则 | 一句话说白了 |
|---|---|
| 不用 5 块结构 | 面试页不是任务记录，不用 `INFO_SUMMARY_HTML_RULES.md` 的“结论 → 主图 → 状态 → 时间线 → Q&A”；按下面两行的结构写。 |
| 综合页结构 | 顶部结论 → `目录`（图 1）→ `开始前`（时间表、怎么听、边面试边看、他的经历）→ `技术题`（最后一张图是名词速查）→ `软技能` → `面试后`（Feedback 表对照图）→ `这个候选人`（最多 2 张图）。 |
| 专题页结构 | 顶部结论和图的导航 → `说白了`（图 1：说白了是这几件事）→ `全局`（用一次真实操作串起主要部件的流程图）→ `补课`（面试题会用到的概念图）→ 一行链接，指到综合页的名词速查。 |
| 说白了是这几件事 | 专题页第一张图给面试官自己看懂每样东西是干什么用的：把 `AGENTS.md` 的“说白了核心是这几件事”画成图，从上往下一层一个方块（第 0 层、第 1 层……），箭头表示要先懂上一层；每个方块写一个问题，再用 Answer Pattern 写“X 解决的是 / 回答的是 ENGLISH（中文）：”和一句话答案；通常 4～8 层；图里出现的每个名词（例如 FSMO、对表来源）都要在某一层用一句话解释，不能只点名；措辞要准确，不能让人误解（例如写“每人一个账号”，不写“全公司一个账号”）；点开写在本页哪张图看细节。它讲“是干什么用的”，不讲步骤，也不讲面试题考什么。 |
| 全用图 | 页面里不放纯文字块：每张卡片只有一行 eyebrow（`图 N：标题`）和最多一句短句，其他内容都在图里，或者点方块后的详情里。 |
| 图的形式按内容选 | 内容本身是有先后的步骤，才画流程图；不是流程的不硬做成流程图，从 `HTML_PAGE_RULES.md` 的 `常用图形` 里选最贴切的（例如：包含关系用层级图，东西在哪个网络用分区架构图，几点不分先后用检查清单，比大小用进度条或柱状图，两种做法比较用对比卡片）。Human 更喜欢流程图，所以内容是流程时一定用流程图。 |
| 不重复的图 | 同一个流程只画一次。某道题问的流程已经画过，这道题只画追问和打分，并写明对照哪张图；名词速查只放图里没画成方块的名词。 |

### 怎么解释名词

| 规则 | 一句话说白了 |
|---|---|
| 不用比喻 | 不用“像公司保安”这类比喻；改成用一次真实操作（例如员工早上登录、一次 Terraform 改动）把部件按顺序串起来，每一步写由哪个部件回答。 |
| 标类型 | 流程图里每个部件方块的右上角写它的类型，例如 Server、服务、软件、配置、DC 的角色、后台过程、文件、身份；图下面用一两行文字说明每种类型是什么意思。为什么：面试官分不清某个名词是一台机器、一个服务还是一项设置。 |
| 回答的是 / 解决的是 | 点开任何名词，第一行用 `AGENTS.md` 的 `Answer Pattern`：`X 解决的是 ENGLISH PROBLEM（中文问题）：` 或 `X 回答的是 ENGLISH QUESTION（中文问题）：`，下一句是一句话答案。 |
| 在哪里看得到 | 真实存在的部件（server、服务、软件、配置）在详情里加一行“在哪里看得到”：在哪台机器、哪个管理工具里能看到，Azure 里对应的是什么。 |
| 名词速查 | 名词表放在综合页，是技术题的最后一张图：按专题分块，每块按类型分区；方块上只写名词，点开看解释；搜索时搜到的方块会亮起来。为什么：面试时只看综合页，听到不懂的名词没时间去翻专题页。 |
| 按面试官的基础写 | 面试官不熟的领域按零基础写，第一张图就是操作流程图；面试官熟的领域少解释，只写和面试有关的要点。 |

### 怎么出题

| 规则 | 一句话说白了 |
|---|---|
| 考理解不考背诵 | 好答案是：说得出主要部件、它们的先后顺序、每个为什么重要。命令永远不是打分标准，说不出命令不扣分；命令只能出现在名词解释里，帮面试官听懂候选人提到的命令。 |
| 每题一张图 | 题目尽量问成“讲一遍 X 的流程”，画成流程图：左边是他应该讲到的步骤（深蓝 = 及格要讲到，蓝 = 做过的人才会讲到），右边的追问放在它要追问的那一步旁边。题目本身不是流程（例如职业方向）时，左边改成“好答案要讲到的几点 · 不分先后”的检查清单，不画箭头；eyebrow 末尾写“检查清单”。 |
| 怎么判断写在图上 | 每题图的最下面是“怎么判断 · 看他懂不懂为什么，不看背没背出步骤”：先一行及格线，再并排两块，左边“答得好 · 懂了”、右边“答得差 · 背的或不懂”，各写 3 条看得到的表现，不用点开就能看到。表现要写他懂不懂“为什么”“会影响什么”“出了问题怎么办”，例如“说得出每一步在处理哪个部件”“步骤名字都对，问为什么就卡住”。 |
| 答案标准 | 步骤写“他讲到这些就算”和“为什么重要 / 为什么是加分”；追问写意思、及格、优秀、好在哪、弱在哪；点开“答得好”放一段 English 示例答案和一行“说白了：”中文，点开“答得差”放一句听起来像什么。 |
| 页面语言 | 页面里所有技术术语和专有名词都用 English，其余用中文；包括方块上的类型标签（例如 service、config、DC role）、图里的步骤和详情，例如写 time source、scheduled task、in-place upgrade，不写对表来源、定时任务、原地升级。English 让一行变长时，改短这一行，不缩小字。 |
| 中英文 | 面试题和追问用 English 原话，下面加一行“意思：”中文；方块上的追问写 English 短句和中文短句。 |
| 故意说错 | 技术题里放一两句明显错的说法（例如“新 DC 好了，直接删掉旧 DC 的 VM”），用黄框标出，看候选人会不会礼貌地纠正，还说得出为什么。 |
| 先问他的经历 | 开场后先问一道通用的经历题：“讲一个和这个岗位最相关的近期项目，你负责什么、做了什么”；画成流程图（背景 → 他的角色 → 他做了什么 → 遇到的最大问题 → 结果 → 回头看会怎么改），一样有追问和答得好 / 答得差，时间算在开场里。 |
| 还是要问经验 | 每道技术题也请他讲一个自己做过的真实例子；一直说 we、追问就卡住的，算没做过。 |
| 题目通用 | 题目针对岗位，不针对某个候选人：题目、追问、答案标准里不写候选人的名字、公司和经历，这个岗位的每个候选人都用同一套题。 |
| 候选人只占最后一节 | 当前候选人的内容最多 2 张图，放在综合页最后一节 `这个候选人`，换候选人时只换这一节。建议的 2 张：“他说过的经历 → 用哪道题核实”（自称很强但 CV 里没有证据的用黄框标为“最要核实”），和“他的书面材料”（从 CV 看到的扣分和加分的地方）。 |
| 不写敏感个人信息 | 出生日期、住址、电话、邮箱、签证细节、犯罪或驾驶记录、薪资期望不写进页面；候选人那一节只写和工作能力有关的经历和书面材料。 |

### 软技能题和 Feedback 表

| 规则 | 一句话说白了 |
|---|---|
| 按 Feedback 表出题 | Human 给了面试后要填的 Feedback 表时，表里每一块（例如 Communication、Consulting fit、Culture、Growth）出 1～2 题，同样做成流程图；表里不适用这个岗位的项（例如编码测试）不出题。 |
| Communication 不单独问 | Communication 用一张“边面试边看”检查清单记录（有没有答非所问、要不要重复问题、先说结论吗、说 I 还是 we、会不会纠正说错的话、CV 写得整齐吗），再加一道“讲给不懂技术的人听”的题。 |
| 价值观对到步骤 | 公司价值观题，在流程的每一步标上它对应哪条价值观，面试后能直接填表。 |
| Feedback 表对照图 | 综合页最后一张图：左边是 Feedback 表的每一块，右边是证据在哪几张图；点开看表里问什么、怎么写、哪些这次没考。 |
| 填好的 Feedback 表的长度 | 面试后 AI 写给 Human 直接粘贴的 Feedback 表：不设硬单词上限，因为单词数一卡死，AI 会先删主语、堆名词，读起来不像面试官说的话（2026-11-13 Human 定，和 `AGENTS.md` 的 `长度靠例子，不靠字数` 一致）。不写太长：每一项先抓住重点，只写最能支持结论的 1～2 个点，一般一两句，Technical 是最重的一项，可以多一句；照 Human 用过、认可的 Feedback 表当例子写。 |
| Feedback 表和结论一致 | 每一项的语气都要和 Overall 的结论一致。结论是 Hire 时，每一项只写优点，Growth 也一样：写他带过谁、愿意学、自己在学什么，不写“需要什么支持”；要补的地方写进给 HR 的消息和反馈页，不进表。Human 没要求时，表里不写级别建议（例如 I'd see him at Senior level）。结论是 No hire 时反过来：每一项都写清楚不够的地方，语气见 `Feedback 表的语气`。为什么：表里缺点写多了，Hire 的结论看起来就站不住。 |
| Feedback 表的用词 | 不重复这一项的名字（例如 Communication 那项不写 communication skills，直接写 Easy to talk to and explains things clearly.）；每句都有主语（写 He has solid hands-on experience with Terraform…，不写 Strong hands-on Terraform experience… 或 Looks after…）；不堆术语清单（例如 plan-only CI, approval gates and Checkov scans）；不用花哨的说法、副词和夸大的词（例如 second nature、sensibly、big、even），用普通的话；句子之间用 also、as well、before 这类小词接上，读起来连贯；不写候选人什么时候能入职。 |
| Feedback 表的时态 | 按事情发生的时间选时态：以前做过的用现在完成时，常加 before（He has run a Data Factory platform day to day before.）；一直在做的用现在完成进行时（He's also been building his own AI lab at home.）；性格和习惯用一般现在时（He stays calm when there's a disagreement.）；面试里讲的某一次经历用过去时（After a production incident, he worked on fixing the process.）；说他来了以后会怎么做用 will（When a deadline is tight, he will work out what matters most and what can wait.）。为什么：面试里听到的是过去的经历，写成 He runs… 就变成在说他现在的工作，不一定对。 |
| Feedback 表的语气 | 事实要直白，语气不能直给。结论是 No hire 时，这一项有真的优点，就先写他会的、做得好的，再用 but 写不够的地方（He knows the general steps for moving a Windows server, but he wasn't sure of the order when replacing a domain controller.）；没有优点的项直接写事实，不硬找。优点要和反馈页的证据一致，例如反馈页判断他表达一般，就不写 easy to talk to；也不写借优点说缺点的话，例如 honest about his gaps。给 HR 的消息也一样：先一个真的优点，再写结论，结论在第 1 段。为什么：Human 2026-11-11 说只写缺点太直给，读的人会觉得不客气。 |

### 时间

| 规则 | 一句话说白了 |
|---|---|
| 先问时间 | 先问 Human：整场多长、技术题多长、软技能和候选人提问算不算在技术时间里。 |
| 时间表 | 综合页第一张图是时间表：每一段画进度条，写分钟数；技术题时间单独框起来；点开每一段写“超时了砍哪题”。 |
| 每题标时间 | 每道题的 eyebrow 写“必问 / 备用”和大约几分钟；面试官最擅长的领域给最多时间。 |

### 导航

| 规则 | 一句话说白了 |
|---|---|
| 目录图 | 第一节是目录图（图 1）：按 开始前 / 技术题 / 软技能 / 面试后 / 这个候选人 分区，每个区里按话题一行，每张图一个方块（必问蓝框、备用灰框），点方块跳到那张图。不在大标题下面列一长串链接。 |
| 顶部导航栏 | 第一个是共用 `summary.js` 自动生成的下拉“目录”（列出每一块和每张图，目录图也在里面），页面不手写目录链接；后面是每张关键图的短名字，1280px 宽时一行放得下；它固定在页面顶部（共用 CSS 的 sticky），看到哪道题都在；手机上收进三条横线菜单。 |
| 跳转不被挡住 | 跳到某张图时，图的标题要露在顶部导航栏下面：在上一张卡片的末尾放一个空的 `<span id="fN"></span>` 当跳转点；每一节的第一张图用 section 的 id。 |

## Conditional Requirements

| 条件 | 必须做 |
|---|---|
| 没有 CV 或电话筛选记录 | 不写 `这个候选人` 那一节，在回答里说明缺什么。 |
| Human 没给 Feedback 表 | 软技能题按 JD 里写的软技能出 1～2 题；不画 Feedback 表对照图。 |
| 同一个岗位有多个候选人 | 题目部分只有一份；`这个候选人` 那一节每人一份，按面试日期排，目录里每人一行。 |
| 页面里引用了外部事实（产品支持日期、功能限制） | 写明出处（例如 Microsoft Learn）放进页脚；没核实的写 `UNVERIFIED`。 |
