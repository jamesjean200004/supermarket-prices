# HTML_PAGE_RULES.md

触发条件：Human 要求 AI 做任何网页 / HTML 页面（包括信息汇总；信息汇总另外再读 `INFO_SUMMARY_HTML_RULES.md`）。入口见 `AGENTS.md` 的 `规则索引：什么任务读哪个文件`。

来源：2026-10-27 v-project 里做的几个蓝色信息汇总 HTML（Human 评价"非常清晰"）；2026-10-30 用 AZZU-3296 汇总做的版式试验（Human 选了 Apple 官网的版式，配 Material 蓝，评价"非常满意"）；借鉴了 progressive disclosure（默认只给需要的，细节按需出现）。

## Always Mandatory

### 先让人一眼看懂

- **3 分钟拿到重点**：读者 3 分钟内能看懂 high level 信息；第一屏只放结论，往下先看到全局的图。
- **字少，重点突出**：每一块先给结论；一个页面只突出 1～2 个重点。读起来有负担，就是字太多。
- **细节默认收起**：能折叠的都默认折叠（Q&A 的答案、检查清单、详情、试过不行的方案等），点 "+"、点方块或搜索时才出现；理解整体关系必需的信息不能藏。
- **图优先，其次表，最后才是段落**：能用图说清楚的不写成文字；能用表的不写成段落。关系、结构、架构、流程都画成图，不用文字描述。
- **图的形式按内容选**：先想清楚要讲的是什么（对象之间的关系、步骤、时间、数量、对比），再从下面 `常用图形` 里选最合适的；可以组合；清单外的图确实更合适时也可以用；不为凑数画没有信息的图，也不固定用 draw.io 式方框箭头。
- **先全貌，后细节**：每张图都先让人看到大结构，再看细节（2026-11-07 Human）。“最多 5 个”数的是第 1 层的大组（流程的 Stage、关系图的列或分区框、层级图的顶层），组里面的小方块不算。按图的类型选做法：
  - **步骤流程画成两列，Steps 默认收起**（2026-11-09 Human；2026-11-16 大步骤改叫 Stage、小步骤改叫 Steps，见 `AGENTS.md` 的 `Stage / Steps 和用时`）：用 HTML 方框画，不用 SVG，展开收起时页面自动排版，手机上也不用横着滑。左列是 Stage 方框，从上往下排，用带箭头的线连；每个 Stage 右边是它自己的 Steps 分组（灰底大框），用分叉线连到每个 Step。Steps 默认收起；点 Stage 展开或收起它自己的 Steps，图上方有一个“全部展开 / 全部收起”按钮；搜索命中 Step 时自动展开。第 1 层最多 5 个 Stage，Steps 不算；只有 Stage 和 Step 两层，Step 下面不再分层。手机上 Steps 排到 Stage 下面时也要明显往右缩进，一眼看得出是哪个 Stage 的。每个方框一句话说做什么；命令、预期结果放进点开的详情。写法照 `prompts/common-prompts/templates/STEP_FLOW_DIAGRAM_EXAMPLE.html`。
  - **步骤上标状态**：流程 / 步骤图的每个 Stage 和 Step，方框最左边、标题前面写状态 emoji 加两三个字：`✅ 做完`、`🟡 在做`、`❌ 失败` / `❌ 卡住`、`⬜ 待做`（定义见 `AGENTS.md` 的 `步骤状态 emoji`；2026-11-15 Human 定，取代 2026-11-10 的彩色圆点；2026-11-16 去掉 `⏳`）；emoji 后面有字，不用图例；要等别人的步骤仍用黄色虚线框和虚线。
  - **步骤上标用时**：任务做过的每个 Step 方框上写 `用了 N 分 M 秒`，等得久的写 ⏰ 和在等什么；开始、结束时间和等了多久写在点方块弹出的详情里，Stage 的详情写总用时（规则见 `AGENTS.md` 的 `Stage / Steps 和用时`）。
  - **步骤都要编号**（2026-11-10 Human）：Stage 和 Step 的标题最前面都写编号。Stage 写 `Stage 1`、`Stage 2`；Step 写所属 Stage 的编号加自己的序号，例如 `Step 1.1`、`Step 1.2`、`Step 2.1`。点开的详情标题用同一个编号。这样说哪一步时直接说编号就行。只是说明、不是步骤的方框（例如“这一步会建什么”）不编号。
  - **有上下级的**：层级、时间线、数量分两层：第 1 层最多 5 个大块，每个一句话说做什么、为什么；第 2 层细节默认收起，点开或搜索时才出现。
  - **讲关系的**：权限、架构里谁连谁这类图，关系本身就是答案，不收起细节；用分列或分区框把大组框出来，图上面一句话说全貌（例如“2 个 Subscription，3 个 identity，6 条 role”）。参考 `prompts/common-prompts/templates/RELATIONSHIP_DIAGRAM_EXAMPLE.html`。
  - **关系图太大**：大组超过 5 个，或箭头交叉多到对不上时，拆成两张：一张画全貌，一张画其中一块的细节。
- **块要少**：顶层块越少越好；放不下的信息放进已有的块里默认收起，不另开新块。
- **文字密度要轻**：每一格、每一行尽量 1～2 句；长的说明放进点击展开或详情面板。
- **名字写具体**：resource、subscription、identity、repo 等写完整的名字和 ID；不知道的写 `UNKNOWN` / `UNVERIFIED`，不猜。
- **用词**：给 Human 自己看的页面，技术名词、Azure 等平台的 resource / service 名称和术语用 English，其余用中文；给团队看的页面全部用 English。

### 常用图形

网页、信息汇总和回答卡片里的图都从这张表里选。只能用 Markdown 时，用 emoji 列表加箭头、文字进度条和表格代替，不放进代码块（写法见 `AGENTS.md` 的 `Markdown Diagram 不用代码块`）。

| 类别 | 图形 | 什么时候用 |
|---|---|---|
| 关系 | 组件图（架构图，Component diagram） | 谁调用谁、数据怎么走 |
| 关系 | 分区架构图 | 东西在哪个环境、Subscription、网络里 |
| 关系 | 层级图 | 上下级、包含关系 |
| 步骤和时间 | 流程图（Flowchart） | 步骤和分支 |
| 步骤和时间 | 决策树（Decision tree） | 怎么一步步判断 |
| 步骤和时间 | 时间线（Timeline） | 什么时候发生了什么 |
| 数量 | 进度条 | 完成度、用量对上限（写实际数值和单位） |
| 数量 | 数字卡片 | 几个关键数字 |
| 数量 | 柱状图 | 几个类别比大小；几项数字一起对照用分组柱状图 |
| 数量 | 折线图 | 随时间的趋势 |
| 数量 | 点状图（Dot plot） | 几个值放在同一条刻度上，看谁高谁低、离目标多远 |
| 对比和检查 | 对比卡片 | 方案对比、改前改后 |
| 对比和检查 | 检查清单 | 逐项是否通过 |

- **关系看得出来**：图要让人一眼看出东西之间是什么关系：步骤和调用用箭头连起来；比较用对比表，行是比什么，列是方案。
- **每张图标图号**：页面里每张图的标题都写 `图 N：标题`，N 从 1 起按页面顺序编；文字提到这张图时写一模一样的 `图 N`，不写“上图”“下面这张图”；给团队看的页面用 `Figure N`（规则在 `AGENTS.md` 的 `图号`）。
- **卡片一行一张**：卡片从上往下排，一行只放一张，不左右并列（数字卡片也一样）。左右并排的卡片看不出是什么关系，也不知道先读哪张。
- **多张卡片先说关系**：一块里有两张以上卡片时，卡片上面先用一句话说清三件事：这几张卡片是什么、为什么放在这里、它们之间是什么关系（例如按先后顺序、一个总数拆成几部分、几个场景对比、几件互不相关的事）。看的人不用自己猜为什么有这些卡片。

### 版式：Apple 官网式布局，配 Material 蓝

- **整体**：参照 apple.com 产品页：大留白；白底和淡蓝灰底的 section 交替；白色大圆角卡片从上往下一张一张排；靠字号对比分层级。不用背景图片和视频，加载要快。
- **不要寡淡**：2026-10-27 的灰白版和 2026-10-30 的纯 Apple 灰色配色，Human 都觉得不如蓝色清楚；清楚优先于极简。
- **颜色只有这几种**：红、黄、蓝、绿 4 种主色，加上紫色（只表示"要团队"这一种状态），再加白和灰（背景、文字、线条）；每种可以用深浅不同的色调（例如浅黄、深黄），但不再加别的颜色（不用青绿、橙、粉等）。颜色定义成 `:root` CSS variables。
- **蓝是主色**：Material 蓝 `#1976d2` / `#42a5f5`，深蓝 `#0d47a1`；顶部结论区用蓝色渐变（渐变只用在这里），section 标题、链接、主要连线用蓝。区分类别（例如 Task 1 / Task 2）用蓝和深蓝，不借用状态色。
- **白和灰**：大部分背景是白色，另一部分 section 用淡灰底（例如 `#f4f7fb`）拉开层次；正文近黑 `#1f2937`，次要文字灰 `#5f6b7a`，线条浅灰。
- **状态色**：红、黄、绿、紫只用在状态上，用约 10px 的小圆点加文字：绿 = 完成 / 已确定，黄 = 待确认，紫 = 要团队（等团队做或定），空心灰圈 = 待做，红 = 先处理 / 有风险。红色只给真正要先处理的事，整页尽量只出现一次；不用整块彩色底；图旁边放图例。
- **字体**：`"SF Pro Display"` / `"SF Pro Text"`, `-apple-system`, `BlinkMacSystemFont`, `Inter`, `"Helvetica Neue"`, `Arial`, `"PingFang SC"`, `"Noto Sans SC"`, `"Microsoft YaHei"`, `sans-serif`；Apple 设备上英文用 SF Pro、中文用 PingFang SC，和苹果官网一样；其他设备上 SF Pro 和 PingFang 不能由网页加载（授权不允许），所以从 Google Fonts 加载最接近的 `Inter`（英文）和 `Noto Sans SC`（中文，即思源黑体）；代码用 monospace。
- **字号层级**：按下表；所有文字（包括 SVG 里的字、表格、代码）不小于 16px。

| 层级 | 电脑 | 手机 | 字重 | 字间距 |
|---|---|---|---|---|
| 顶部结论 | 30px | 24px | 600 | -0.01em |
| Section 标题 | 28px | 23px | 600 | -0.003em |
| 卡片大字 | 24px | 21px | 600 | 0 |
| 卡片说明 | 19px | 18px | 600 | 0.007em |
| 副标题 / 引导语 | 17px | 17px | 500～600 | 0.01em |
| 正文 | 17px，行高 1.47 | 17px | 400 | -0.022em |
| 小字 | 16px | 16px | 400～600 | 0 |

- **间距**：section 上下 120px（手机 72px）；顶部结论区上下 64 / 48px（手机 44 / 36px）；卡片内边距 40px（手机 28px）；卡片之间 24px（手机 16px）；内容最大宽度 1080px，两边留 22px。
- **卡片**：圆角 28px（手机 20px），不加阴影；淡蓝灰底的 section 里放白卡，白底的 section 里放淡蓝灰卡。
- **导航栏**：顶部固定，半透明白底加 blur；左边写页面名，右边是各块的链接和一个小搜索框；信息汇总的导航栏第一个是“目录”（见 `INFO_SUMMARY_HTML_RULES.md` 的 `本页目录`）。手机上链接收进三条横线的菜单，点开下拉，点链接或按 Esc 收起；搜索框保留。
- **特效要克制**：每块进入屏幕时淡入并上浮一次（约 0.8 秒）；方块 hover 放大 1%（0.3 秒，`cubic-bezier(0, 0, .5, 1)`）；展开时 "+" 转成 "×"；点方块后背景变暗、详情从屏幕底部弹出。只动 `opacity` / `transform`，并支持 `prefers-reduced-motion`（全部关掉）。
- **不要**：背景图、视频、顶部以外的渐变、卡片阴影、粗边框、左右并列的卡片。
- **Emoji**：页面里不用 emoji，标题也不加；状态用颜色小圆点加文字表示。
- **能点的东西有反馈**：hover、键盘 `:focus-visible` 都要有样式。
- **手机能看**：窄屏改成单列；宽的图放在能横向滑动的容器里，字号不缩小；长的名字、ID 要能换行（`overflow-wrap: anywhere`，flex / grid 子元素加 `min-width: 0`），页面不能出现横向滚动。
- **两个宽度都要看**：交付前在 375px 和 1280px 以上的宽度各看一次。

### 从模板开始

- **先复制模板**：做信息汇总或类似的单页汇总时，从 `prompts/common-prompts/templates/INFO_SUMMARY_TEMPLATE.html` 复制开始，只换内容；样式和脚本在 `info-summary/assets/` 的共用文件里，页面里不再写一份，这样省 token，各项目的样式也一致。
- **模板跟规则一起改**：版式规则变了，模板在同一个 PR 里一起改。

### Human 指定的内容

- **Human 可以随时加 section**：Human 说要加哪个 section，这是允许的，就单独加这一块，不省略、不并进别的块；信息汇总里它不算在固定的 5 块里（见 `INFO_SUMMARY_HTML_RULES.md` 的 `页面结构`）。

### 代码和已有文档

- **页面里不放代码**：能运行的脚本、policy 定义、配置等放在页面外面的单独文件里，页面只写它是干什么的，再链接过去。脚本文件放在项目根目录的 `scripts/`（见 `CODING_STANDARDS.md` 的 Scripts in `scripts/` 规则）。只有一两行的短命令可以直接写在页面里（例如触发 policy 扫描的命令）。
- **已有的文档不重写**：要讲的内容已经有文档了（例如 policy 文档、Runbook），页面里只写步骤或结论，再链接到那份文档；不在页面里再写一份。

### 易于检索

- **一眼找到在哪**：每一块用一个短标题开头；导航栏能跳到各块。
- **能搜**：导航栏里放小搜索框；搜索时过滤和高亮匹配的内容，自动展开命中的收起内容，图里相关的方块也高亮。
- **按问题写**：查找类内容写成"问题 | 答案"，问题用 Human 会搜的说法写，例如"Prod pipeline 的 identity 叫什么？"。
- **方便复制**：名字、ID、命令用 `code` 样式显示，点一下就能复制。命令（`<code class="cmd">`，或详情数据里写成 `[字段, 命令, "cmd"]`）旁边还有一个“复制”按钮，点一下复制到剪贴板（2026-11-09 Human）。命令放在它所属的 Step 里，不另做一个“所有命令”清单。
- **资源链接直达那一页**：页面里提到 Human 可能要去看或操作的东西（Azure resource、Pipeline run、PR、ticket、ADO / GitHub 页面等），链接直接打开这个东西的那一页，例如 Azure Portal 里某个 Vault 的 Backup instances 页；不只链到首页或列表页，让 Human 自己再找。Azure Portal 链接写上 tenant 和完整的 resource ID。为什么：Human 点一下就到要看的地方（2026-11-16 Human 说这样做得非常好）。

### 文件和交付

- **一个文件**：一个自包含的 `.html`，本地双击就能打开；外部资源只用 Google Fonts，页面自己用的 CSS / JS / SVG 全部写在文件里。
- **信息汇总例外**：信息汇总的 CSS / JS 只引用本 repo `info-summary/assets/` 的共用文件，页面里不写（见 `INFO_SUMMARY_HTML_RULES.md` 的 `共用样式和脚本`）；页面和 `info-summary/assets/` 在同一个 repo 里，本地双击照样能打开。
- **交付前实际看一遍**：在浏览器里打开检查，修掉文字重叠、截断、连线穿过方块、手机菜单打不开等问题后再交付；没办法预览时，明确告诉 Human 没有实际看过。
- **Repo 里的 HTML 也遵守项目规则**：文件名、日期、commit 规则按 `MARKDOWN_DOCUMENT_RULES.md` 和 `PROJECT_LOCAL_OVERRIDES.md`。

## Scenario-Based Mandatory

### 信息汇总

- **另有规则**：做或更新信息汇总 HTML 时，除了本文件，还要遵守 `prompts/common-prompts/rules/INFO_SUMMARY_HTML_RULES.md`，写完按 `prompts/common-prompts/review/INFO_SUMMARY_HTML_REVIEW.md` 检查。

### 测试步骤页

触发条件：页面要讲怎么做一个或几个测试（例如 policy 的 Audit 测试和 DINE 测试）。来源：2026-11-09 Human 对 AZZU-3296 Sandpit 测试步骤页的要求。

- **Stage 写明是哪个测试**：一页有几个测试时，步骤流程图的 Stage 直接写是哪个测试、用哪些测试对象（例如“2 Audit 测试 · 账号 B A E C”），看图就知道哪一步在测什么。
- **测试对象按测试分列**：讲测试对象（账号、资源）的图，每个测试一列，列里放这个测试用到的对象，每个对象写预期结果；两个测试都用的对象，两列都放。
- **Happy path 放前面**：每个测试先放、先测 Happy path（预期一切正常的那个对象），再放失败的情况。

### 项目自己的样式

- **项目可以改**：项目需要不同的颜色或样板时，写在该项目的 `PROJECT_LOCAL_OVERRIDES.md`，只写和本文件不同的地方。
